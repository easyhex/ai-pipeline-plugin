# ai-pipeline — руководство

Плагин для Claude Code: пайплайн AI-разработки из 12 команд для тяжёлых, расчётных, «взрослых» систем. Три идеи, на которых всё стоит:

1. **Ни строчки кода без вашей подписи.** Пайплайн сначала интервьюирует вас до общего понимания, проигрывает спеку на явное «да» — и только потом едет автономно.
2. **Улики до утверждений.** Каждое «готово» подкреплено исполненной командой, каждое численное требование — прогнанным оракулом, каждый вердикт гейта — файлом, который можно перепроверить.
3. **Всё — артефакт для человека.** Требования (ФТТ/НТТ) с историей изменений, трассируемость до merge-SHA, риск-реестр, решения (ADR), уроки. Через год можно ответить «почему F-014 такая и что это доказывает» без археологии.

## Установка (один раз на машине)

```bash
claude plugin marketplace add easyhex/ai-pipeline-plugin
claude plugin install ai-pipeline@ai-pipeline-marketplace
```

Системные инструменты (плагин их **детектит и подсказывает**, но не ставит сам):

```bash
brew install beads     # bd — задачи и зависимости, переживающие сессии
brew install uv        # для Serena (память проекта); serena-agent /init поставит сам
# node 18+ — для Playwright MCP (визуальный гейт фронтенда); jq — есть почти везде
```

Четыре плагина-зависимости (`superpowers`, `beads`, `context7-plugin`, `template-bridge`) `/init` установит сам с подтверждением `[y/n]`.

## Быстрый старт: два сценария

**А. Новый проект (пустая папка):**

```bash
mkdir my-app && cd my-app && claude
> /init "решатель разреженных СЛАУ с итерационными методами"
```

**Б. Существующий код (adopt-режим):** та же команда в папке проекта. `/init` увидит код и предложит адоптировать: Master Plan будет **выведен из реального кода и git-истории**, существующие файлы не перезаписываются (`.gitignore` дополняется, настройки сливаются), коммитятся только файлы пайплайна — и каждая выведенная строка идёт к вам на построчное подтверждение. Уже существовавшая функциональность помечается `shipped pre-adoption` (базлайн: `/release` её не сметает в changelog, `/validate` покажет как «unfalsifiable», пока вы не добавите требования через `/plan-improve`).

В обоих случаях `/init` проведёт **интервью frontier-раундами** (см. «Как отвечать» ниже): ставки проекта → класс (numerical-library / simulation / data-pipeline / service / ui-app / cli) → пользователь и стек → сценарии → ранжирование качеств → **принудительный НТТ-раунд** (допуски с единицами, масштабы данных, детерминизм — это спрашивается всегда, потому что сами LLM такое не вытаскивают). Класс проекта настраивает гейты: вычислительные классы получают `docs/model.md` и обязательный квантитативный гейт, а визуальный — пропускают.

## Главный цикл: `/feature`

```
> /feature "предобусловленный CG с остановкой по относительной невязке 1e-8"
```

| Фаза | Что происходит | Ваше участие |
|---|---|---|
| 1 ground | читает Master Plan, требования, уроки (дистиллированные правила первыми), глоссарий, риски, аналоги, отказы, память Serena, доки библиотек; печатает баннер `Layers: …` | — |
| 2 интервью | frontier-раунды вопросов; факты агент ищет сам, решения — только ваши; спека по схеме `SPEC_FORMAT.md` | **отвечаете на раунды** |
| 3 критик-1 | senior-critic ревьюит спеку (EARS-критерии, аналоги, глоссарий, риски, провенанс, математика) | только если Critical |
| **3.5 playback** | **единственная обязательная остановка**: дайджест — ваш запрос дословно / решения / допущения машины / out of scope / швы-инварианты-допуски / открытые TBC. На «да»: минтится F-ID, создаётся живой файл требований, подпись коммитится | **явное «да»** |
| 4–7 | план (у численных задач — обязательный тип оракула и обоснование допуска) → beads-задачи → ветка/worktree → TDD-цикл с коммитом на каждый GREEN | — |
| 8 критик-2 | ревью диффа; при Critical — fresh-context верификация находок (до вас доходят только воспроизведённые) | если находки требуют решения |
| 9/9b/9c verify | тесты/линт/сборка → визуальный гейт (фронтенд) → **квантитативный гейт**: доказывающие команды НТТ по сидам, pass^k, run-manifest, advisory-мутации | — |
| 10–11 finish | merge (или PR), статусы, строка в `TRACEABILITY.md` | `git push` — всегда вручную вы |

После подписи на 3.5 пайплайн останавливается только на находках критика, требующих вашего решения, или на сбоях. Хуки плагина страхуют механически: мердж не пройдёт при провальном вердикте гейта или незакрытых Critical без записанного решения.

## Как отвечать на вопросы (это важно)

Вопросы приходят **раундами**, нумерованными, каждый с рекомендацией:

```
❓ 1. Целевая точность решения?
От неё зависят оракулы и критерии остановки.
➡️ Recommended: rel. error ≤ 1e-8 против аналитического решения — стандарт для CG на SPD-матрицах

❓ 2. Детерминизм?
➡️ Recommended: seeded-statistical (бит-в-бит не требуется)
```

Отвечать можно номерами и коротко: **«1 да, 2 второй вариант, 3 нет — потому что …»**. Согласны со всеми рекомендациями — так и скажите: «всё по рекомендациям». Предпочитаете по одному вопросу за раз — добавьте в CLAUDE.md проекта строку `When grilling, ask one question at a time.`

**Вес церемонии** (`light | standard | deep`) спрашивается в первом раунде с рекомендацией из настроек проекта: на `light` спека минимальна и дайджест — 3 строки, но подпись обязательна всегда; на `deep` — дополнительный раунд по краевым случаям.

**Решения на гейтах критика:** `continue` (принять и ехать — решение запишется в отчёт), `address` (доработать: пайплайн сам создаст задачи и вернётся в TDD), `override` (принять риск — потребуется письменная причина, строка автоматически ляжет в `docs/risks.md` с условием пересмотра).

## Карта команд: когда какая

| Команда | Когда |
|---|---|
| `/init "<описание>"` | старт: пустая папка или adopt существующего кода |
| `/feature "<что>"` | новая функциональность — главный цикл |
| `/improve "<что изменить>"` | изменение существующего поведения (амендит живые требования; намеренный слом — через `/deprecate`) |
| `/fix "<баг>"` | отладка через systematic-debugging + автоматический урок в конце |
| `/plan-improve "<правка плана>"` | любая правка Master Plan: архитектура, roadmap, риски, аналоги, глоссарий, model.md — с версией и историей |
| `/validate [фича]` | спросить у реальности: критерии успеха shipped-фич против свидетельств; промахи → предложение репритеризации |
| `/deprecate "<фича>"` | намеренно вывести/сломать: impact-скан, план миграции, BREAKING → мажорный бамп |
| `/release` | срез релиза: semver, человеческий CHANGELOG, дифф требований по mid, локальный тег |
| `/resume [slug]` | продолжить прерванный прогон — позиция выводится из артефактов, не из памяти |
| `/questionnaire "<тема>"` | опросник для клиента/эксперта — требования из чужой головы; отвеченный файл подхватится ground-фазой |
| `/lesson` / `/lesson distill` | урок вручную (редко) / скомпилировать кучу уроков в правила |
| `/remember "<факт>"` | факт в память Serena (редко — обычно пишет критик сам) |

Внутренние фазы (`/brainstorm`, `/plan`, `/critic`, `/verify`…) командами не являются — они живут внутри перечисленных.

## Для расчётных систем — что здесь специально для вас

- **EARS-критерии приёмки** («When cond(A) > 1e8, the solver SHALL switch to QR») — обязательны на standard/deep; критик флажит нарушение грамматики и допуски без единиц.
- **Таксономия оракулов** (`docs-meta/NUMERICS_TESTING.md`): аналитический частный случай / manufactured solution / свойства-метаморфизм / эталонная реализация / порядок сходимости. План обязан назвать тип оракула для каждой численной задачи; «допуск подогнан, чтобы тест прошёл» — именованный stop-condition.
- **Квантитативный гейт (9c)**: каждая НТТ несёт доказывающую команду; прогон по сидам с pass^k; вердикт `verified` только если каждый заявленный оракул реально исполнен (иначе `partial`); run-manifest фиксирует SHA, сиды, платформу, версии, хэши входов. Advisory-мутационное тестирование ловит тесты-пустышки.
- **Критик знает численные режимы отказа**: точное сравнение float → Critical, солвер без оракула → Critical, несидированная стохастика, NaN/Inf на границах API, «tolerance fraud»; двухэтапный карантин — сначала трассирует ваш дифф, потом читает, что спека о себе рассказывает.
- **Верификация ≠ валидация**: спека обязана нести `## Mathematical approach` (метод + обоснование устойчивости + план валидации на данных, отличных от юнит-оракулов), а `/validate` потом спросит у реальности.

## Память и обучение

Каждый `/fix` заканчивается уроком; `/lesson distill` компилирует накопленное в короткие правила (`docs-meta/DISTILLED.md`), которые ground читает первыми — куча не растёт в контекст бесконечно (баннер Layers показывает undistilled-счётчик). Критик на гейтах предлагает памяти (конвенции, решения) — решения дополнительно ложатся коммитаемыми ADR. Отказы — в out-of-scope. Итог: система перестаёт повторять ошибки и переспрашивать решённое.

## Если что-то пошло не так

- **Сессия умерла посреди прогона** → `/resume`: позиция выводится из артефактов на диске (подписанная спека не переигрывается, F-ID не переминтится).
- **Хук не даёт закончить сессию/смержить** → он говорит почему: допишите вердикт гейта, примите решение по находкам, либо сознательно бросьте прогон — `rm docs/superpowers/runs/current.json` (все хуки встанут по стойке «вольно»).
- **Слой отвалился** (Serena, Playwright, bd) → баннер `Layers:` покажет ✗, пайплайн продолжит в деградации и подскажет команду починки.
- **Пайплайн сделал не то** → это материал для `/fix` (баг + урок) или `/plan-improve` (не тот план).
